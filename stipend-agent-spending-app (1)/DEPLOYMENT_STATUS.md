## Security assessment

**Deployed V1 source was unavailable**, so the actual deployed contract cannot be audited. The prior task's proposed `Stipend.sol` design, *if deployed unchanged*, has these defects:

1. `owner = msg.sender` sets the deployer as owner. The passkey can call `revoke()` only if the deployed owner equals the verified Mera human address; neither can be checked without a contract address and authenticated passkey session.
2. `transferFrom(agent, to, amount)` pulls agent-held tokens. The agent can call the token's `transfer` directly and bypass the contract caps/allowlist entirely. An allowance is **not escrow**. V1 cannot fully enforce agent spending limits on-chain.
3. No contract-held balance and no owner recovery path for unused agent-held funds. `revoke()` prevents future `pay()` calls but cannot stop direct transfers by the agent.
4. Agent-only `pay`, payee restrictions, replay mapping, total/per-payment/daily/hourly bounds, and revert-atomic counters look reasonable in the supplied draft, but the on-chain runtime is unverified. Reverted EVM transactions cannot persist `Refused` events; off-chain denial logging is required. A caller-supplied arbitrary quote hash does not itself lock recipient/amount/token to a user-approved quote.
5. The current app's local signer is unauthenticated by passkey on the server and should not be used as a production signing path; no trusted server-side agent signing secret is configured.

**V2 prepared locally, NOT deployed:** `stipend-contracts/src/StipendV2.sol` and `stipend-contracts/src/MockAUSD.sol` (test double only), with notes in `stipend-contracts/README.md`. V2 takes an explicit nonzero intended passkey owner, escrows tokens via owner-only `fund`, permits owner-only payee and agent updates, prevents direct agent transfer of escrow, enforces per-payment/total/daily/hourly/replay/revocation on-chain, binds quote hash to chain/contract/token/recipient/amount/nonce, safely handles ERC-20 return values, guards external calls against reentrancy, and allows owner recovery after revoke. It deliberately has no on-chain `Refused` event because reverts discard logs. The owner address still needs **actual passkey validation before any eventual deployment**. No new external Solidity library was silently introduced.
